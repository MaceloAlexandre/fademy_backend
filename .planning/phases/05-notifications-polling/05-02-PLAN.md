<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → GET /api/notifications | Polling + list fetch; server already scopes by JWT userId (plan 05-01). Client must not trust/derive other users' data |
| browser → PATCH /api/notifications/:id/read | Client sends an id it received in its own list; server enforces ownership (plan 05-01) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05F-01 | Information Disclosure | useNotificationPolling / list fetch | mitigate | Relies on server-side userId scoping (T-05-01); client renders only what the JWT-scoped endpoint returns, never constructs cross-user queries |
| T-05F-02 | Tampering/IDOR | NotificationCard mark-read | mitigate | Client patches only `notification._id` from its own rendered list; server 403-guards ownership (T-05-02). No client-side authority assumed |
| T-05F-03 | Denial of Service | 5s polling interval | accept | D-08 explicit user decision (demo responsiveness); fetch uses `limit: 1` (cheap count), interval cleared on unmount; acceptable for v1 single-institution scale |
| T-05F-04 | Cross-site Scripting | actor name / action text rendering | mitigate | React escapes interpolated text by default; no `dangerouslySetInnerHTML`; avatar `src` from server-issued field only |
| T-05F-05 | Tampering | npm installs | accept | No new packages added (uses existing react-router-dom, lucide-react, axios); legitimacy gate not triggered |
</threat_model>
